# 交付与发布

## 本地交付

每篇保存纯文字正文、来源底稿和一张推荐微信封面。优先沿用项目已有输出目录，文件名包含日期，正文与封面分开保存。封面提示词与实际尺寸也存入同一交付目录，方便后续复用。

用户要求把已有简版整理为Word时，交付DOCX，按牛人、惊喜哥、小惊喜哥、惊吓哥及伤病更新保留来稿顺序与口吻，不额外生成封面、逐场复盘或重复数据附录。每位点评球员配一张本站现有2400×280横条数据卡，包含头像、该场球队、比赛日期、分钟、得分、篮板、助攻、三分、投篮、罚球、抢断、盖帽和失误。优先复用目标项目的 `renderPlayerCard` 和真实完赛数据；不能用AI绘制统计数字，不能把“Image”当成已收到图片，也不能凭模糊短评猜球员。可以从已核实数据直接生成同款卡片；歧义先通过来稿、当日数据或用户补充消除。

DOCX按可用的documents技能制作并逐页渲染检查。逐一核对卡片与点评的人名、比赛、分档和顺序，确认图已嵌入文件且清晰、不跨页割裂。完整数字由卡片承载时，正文不再机械复述；来源和核验记录保存在本地底稿。仅整理已有稿件时不顺带发布网站或创建自动化。

只要求补封面时读取对应稿件，用其主线制作图片，不顺便重写、重发或改变旧文章。修改skill规则也不等于授权覆盖线上内容。

赛程由用户自行写入公众号，简报交付不自动包含赛程文字或赛程图片。独立的赛程导出工具不属于此skill的默认步骤。

## 网站分节标题兼容

新稿默认使用“二、每日惊喜+惊吓球员从夯到拉”和“附录：惊喜+惊吓球员表现明细”。发布前检查目标仓库的 `docs/BRIEFINGS.md` 与正文解析器是否支持这些标题，避免榜单或数据卡片在网站上消失。

若目标网站仍仅识别旧标题，网站上传版本暂用“二、每日惊喜球员从夯到拉”和“附录：惊喜球员表现明细”两个既有分节锚点；它们在旧版接口中仍涵盖惊喜与惊吓。仅适配标题，完整保留两端全部球员、逐人的今日表现/上榜原因、顺序和数据，不缩减为正向名单。附录每人一行的原数据格式继续沿用，DD和A/T在判断与短评中体现。适配后的上传版本单独保存，并按实际发送的全文回读核验。网站已支持新标题时直接使用新名称。

此兼容约定不授权改站点代码、重新部署、发布文章或覆盖历史内容；用户只要求迭代skill时，修改skill及其引用文档即可。

## 写入每日简报

仅在当前请求授权上传/发布时执行。

1. 在实际目标仓库读取 `AGENTS.md`、`docs/BRIEFINGS.md` 和 `.openai/hosting.json`。不把项目ID、凭证或本机绝对路径硬编码进skill。
2. Sites `get_site` 取站点地址及当前授权发布凭证，仅放会话内存。遵循仓库发布脚本，通过隐藏标准输入提供凭证，不写到源码、文件、浏览器、日志或命令参数。
3. 标题与日期单独填写；纯文字正文不重复标题日期，不塞图片、HTML、Markdown强调符号或“Image”。封面图片作为独立交付，不能谎称已上传到仅支持纯文字的接口。用户要求同步到网站时，按目标仓库 `docs/BRIEFINGS.md` 的封面发布步骤处理；若该站采用静态图片登记，则复制封面、登记日期并通过 Sites skill 部署。不要把仅保存到本地说成已上线。
4. 运行既有 `briefing:publish` 脚本，回读核对日期、标题与正文后才报告成功。同一天更新同一篇。上传结果不确定时先读公开接口确认，不能盲目重复发布。

没有发布要求时只保存和交付。只有用户另行要求定时执行，才创建自动化。
